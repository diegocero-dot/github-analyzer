### Round 3 — 2026-05-10 — Discovery during implementation (not from `/analyze-prompt`)

**Status:** ⚠ Runtime discovery — prompt assumption was wrong

This finding did not come from `/analyze-prompt` (which by design audits the prompt statically against the local repo). It surfaced during execution when Claude Code ran `git ls-remote origin` per Step 1.2.

**Finding:**

5. **The GitHub remote is NOT empty.** The prompt's Step 1.2 expected `git ls-remote origin` to return no refs (Diego had stated the repo was created empty). Reality: the remote has `157f916c` on `refs/heads/main`. A direct push of the local baseline would be rejected because of divergent histories (local has `08278f9 chore: initial commit` from the scaffolding step; remote has `157f916c` from GitHub's auto-init).

   Root cause: when the repo was created on GitHub, an init option (README / LICENSE / .gitignore) was likely checked by accident despite the prompt instruction to keep it fully empty.

**Resolution by Cowork:**

- Updated CHANGE 1 Step 1.2 to handle both scenarios: empty remote (push works directly) OR remote with a single auto-init commit (force-push the local baseline using `--force-with-lease`). The repo is brand new, personal, no collaborators, no CI — overwriting the auto-init commit is safe.
- Added an explicit note that this case is expected and how to verify before force-pushing (`git fetch origin && git show origin/main --stat` to inspect the remote commit before overwriting).

**Why this finding matters for the workflow doc:**

`/analyze-prompt` audits prompts against local-repo state and against logical consistency. It cannot reach out to remote infrastructure (GitHub, external APIs, etc.) and verify that distant assumptions hold. **Some findings only surface at execution time**, which is exactly why the workflow includes a verification step before destructive operations like push.

This is also the reason `--force-with-lease` is preferred over `--force`: the lease check guards against a third party pushing to origin between fetch and push.

### Round 4 — 2026-05-10 — Discovery during implementation

**Status:** ⚠ Runtime discovery — multi-account git auth

After Round 3's force-with-lease push was attempted, the push was rejected with a permissions error: git was authenticating as `Diegocero` (the account that hosts the legacy vendor-onboarding repo) but the new repo lives under `diegocero-dot`, a separate GitHub account.

**Finding:**

6. **Multi-account git authentication assumed single-account.** The prompt's CHANGE 1 Step 1.1 added the remote URL but did not verify that the user's git config / credential helper / `gh` CLI was authenticated against the right GitHub account. On a developer machine with multiple GitHub accounts (very common — personal + work, or org separation), credentials cached against one account silently fail to authenticate against another. The local commit (`d7aa773`) is sound; only the push needed a fresh auth context.

**Resolution by Cowork:**

- Updated CHANGE 1 with a new Step 1.0 — "Verify git authentication context before adding the remote" — that prints `gh auth status` and the current `git config user.email`. If the active account does not match `diegocero-dot`, the implementer pauses and asks Diego to run `gh auth login` for the right account before continuing.
- The resolution path uses `gh auth login` because the user already has `gh` CLI configured for the other account and adding a second account is the least-friction path on this machine.

**Why this finding matters for the workflow doc:**

`/analyze-prompt` audits prompts against repository state and logical consistency. It cannot inspect host-level state like git credential helpers, `gh` CLI sessions, SSH agent contents, or keychain entries — these live outside the project and outside the static analysis surface. **Multi-account environments are the canonical case where this matters**: most professionals have 2+ GitHub accounts and assume the right one is active.

Pattern for next prompts that push to a remote in a different org / account: add a Step 1.0 to verify `gh auth status` matches the expected owner of the remote URL before adding the remote.

**Two acceptable cases:**

**Case A — Remote is empty** (no output, exit 0):
The standard path. Proceed to CHANGE 2 normally and finish with `git push -u origin main` in CHANGE 5.

**Case B — Remote already has a commit** (one ref on `refs/heads/main`):
This happens when an auto-init option (README / LICENSE / .gitignore) was checked when the GitHub repo was created. The local history (`08278f9 chore: initial commit` + the new baseline we are about to add) will diverge from the remote.

Inspect what the remote commit contains before overwriting:

```bash
git fetch origin
git show origin/main --stat
```

If the remote commit is the expected GitHub auto-init (README + LICENSE + maybe `.gitignore`), it is safe to overwrite — this is a brand-new personal repo with no collaborators, no CI, and the local baseline we are about to push fully supersedes the auto-init content.

In CHANGE 5 Step 5.4, replace the standard push with a lease-guarded force-push:

```bash
git push -u origin main --force-with-lease
```

`--force-with-lease` only overwrites if the remote is still on the commit we fetched. If a third party pushed something between our `fetch` and our `push`, it fails safely.

**Case C — Anything else** (multiple refs, unexpected branches, auth errors):
Stop and report to Diego. Do not attempt to resolve automatically.

# github-analyzer

CLI and web tool that analyzes any public GitHub repository and produces a technical report on its stack, architecture, technical debt, and documentation quality. Includes natural-language Q&A over the codebase via RAG.

> Status: early development. M0 — Setup + Architecture.

## What it does

Given the URL of a public GitHub repository, the tool:

1. Clones (or fetches via API) the repo and indexes its code into a vector database.
2. Runs a pipeline of specialized agents in parallel — stack detection, architecture analysis, technical-debt review, documentation quality — orchestrated by LangGraph.
3. Synthesizes the individual reports into a structured Markdown report with numeric scores per dimension.
4. Exposes a RAG channel so users can ask natural-language questions about the codebase after analysis.

## Stack

- **Python 3.12+** with strict type hints (`mypy --strict`).
- **LangGraph** — agent pipeline orchestration.
- **Qdrant** — vector DB for indexing and RAG.
- **MCP server** (custom) — GitHub API access with rate-limit awareness.
- **FastAPI** — web backend.
- **Anthropic API (Claude)** — primary LLM provider.
- **Docker** + **Railway** (or Fly.io) — deployment.

Full architecture in [`ARCHITECTURE.md`](./ARCHITECTURE.md) (coming in M0.2).

## Status

Project is in M0 — Setup + Architecture. See [`PROJECT.md`](../PROJECT.md) (workspace-level) for the live roadmap and milestones.

MIT — see [`LICENSE`](./LICENSE).
